# test_glint 评估加速对比 (2026-09-22, 8×RTX4090, cvlface env)

模型: adaface_ir101_webface12m (IR101, 512d) · 数据: /data1/dataset_260918
· test_glint = 8,421,376 图 (60K 类, rec 25G) · val_glint = 1,687,552 图 (12K 类)

## 一、端到端结果 (test_glint 全量 8.42M 图)

| 路径 | 提取 | NxN 匹配 | 全程 |
|---|---:|---:|---:|
| **portable_eval** TRT fp16 + nvjpeg 双流 (单遍, 无 flip) | **150.1s** (56.1K img/s) | **62.8s** (融合核, 564 G对/s) | **~213s ≈ 3.6 min** |
| torch compile max-autotune bf16 (DataLoader, 两遍含 flip) | ~743s (2×388s, 21.7K img/s) | 62.9s (v7 核) | **1325.5s = 22.1 min** |
| torch eager bf16 (val 实测折算) | ~820s (20.6K img/s) | ~63s | ~1400s ≈ 23-24 min (估) |

- portable_eval 比 torch compile 快 **~6.2×**（注意口径: torch 是 normal+flip 两遍；即使按单遍折算 662s vs 213s 仍快 **~3.1×**）
- 匹配侧两者已同为 v7 系核，8.42M 规模持平 (62.8s vs 62.9s, 35.46 万亿对)

## 附4: eval_all_trt_single 是否已用最快速代码 — 逐项审计 (2026-09-22, 全部对照本机实测)

基线: 本机一次 single 启动 227s (engine 54.5 + val_glint 91 + 3×开源集 ~46.7 + tinyface 19.4)

### 已是最快的 ✓
| 组件 | 现状 | 依据 |
|---|---|---|
| type4 NxN 匹配 | v7 CUDA 双桶核 (2000 bins/16384 块) | 生产最快入口; val_glint 4.7s。portable 移植版小规模再快 2.2× (免 pin 拷贝) 但 8.4M 规模持平 |
| flip 处理 | 与 normal 合批单次过 engine | 解码一次、双 forward 合一, 合理 |
| 特征聚合 | /dev/shm + 主进程一次 cat 8 分片 | 无 fabric 磁盘中转问题 |
| CPU 解码 (兜底路线内) | cv2 直解 + 手工归一化, 免 PIL | HF/Folder 路径已是 CPU 解码里的快路线 |
| 同数据集特征复用 | feat_cache (ijbbc/ijbc 共用只提一次) | 已启用 |
| DataLoader worker | fork (免 pickle; rec 分支为本轮修复) | folder 分支注释实测首批 96.9s→0.6s |
| 架构 | 无 fabric/NCCL | 无 barrier 等待/死锁 |

### 不是最快的 ✗ (按损失排序)
| # | 现状 | 最快已知 (本机实测) | 损失/次启动 | 改法 |
|---|---|---|---|---|
| 1 | CPU 解码 DataLoader: val_glint 提取 76.5s (22.1K img/s) | portable_eval nvjpeg 双流+TRT: 29.5s (57.2K img/s, 同 8 卡) | **~30-47s** (视 flip 口径) | 把 portable_eval 的 _nvjpeg_worker 管线接进来 (rec/folder 均支持), 或整个提取换成 el.extract_features |
| 2 | engine 每次启动重建 54.5s, 结束还 rmtree 缓存 | refit: 首次 24s + 0.1s/ckpt (eval_acceleration.md 已验证未集成) | **~54s** | build 前查 engine 缓存 (key=ckpt mtime); 多 ckpt 场景接 refit |
| 3 | 每个评估集独立 spawn 8 worker: 开源集 12K 图付 ~11s, 4 集 ~40s | worker 常驻/复用 (engine 已在 worker 内存里, 换集只需换 dataset) | **~30-40s** | 一次 spawn, 循环喂数据集; 或小集合走单卡省 spawn |
| 4 | bs256 静态 engine + 每批 stream.synchronize() + 无解码/推理流重叠 | bs512 静态 engine (纯推理 7,766 img/s) + 双流 event 重叠 + 攒 64 批 D2H (portable_eval) | 包含在 #1 内 (10-20%) | 换 #1 管线自带解决 |
| 5 | MXFaceDataset tsv 逐行 parse, 每 worker 进程 ~2.3s | portable npy offsets 缓存 0.3-0.5s | ~2s | RecSource 式缓存 |
| 6 | v7 匹配入口每次 pin_memory 全量拷贝 | portable pos_neg_hist_fused (cudaHostRegister) | val_glint 1.7s (4.7→3.0s), 大规模持平 | 换 portable 融合核调用 |
| — | default num_gpu=7 | 本机 8 卡 | 白扔一卡 | 记得 --num_gpu 8 |

### 结论
没有全部用上最快代码。**推理与匹配已是生产最快 (TRT fp16 + v7 核); 慢在三处: CPU 解码管线 (差 2.6×)、engine 每启动重建 (54.5s)、每集独立 spawn (~40s)**。三项都修的理论下限 ~60-90s/次启动 (现 227s), 其中 #1 直接复用 portable_eval 已有代码, #2/#3 是工程量不大的编排改造。

### 踩坑记录 (都已修复, 复发预警)
1. gather 在非 rank0 返回 None → flip 缓存只在 rank0 生效 → 非 rank0 重跑整遍 (522s) → 哨兵修复
2. 分片不等长 (211070/211071) → gather torch.stack 崩 → 分片补齐到 world 整除
3. 单 rank 降级 vs 其余 rank 走 nvjpeg → barrier 错位死锁 (NCCL 空转到 timeout) → 集体表决降级
4. nvjpeg 仅支持 JPEG: PNG HF 集 (cplfw 等) 必须降级 — 如需加速可一次性转 JPEG 重打包
